## 数据与状态

`orders` 保留原记录与查询凭证。新建购买单额外写入 `purchase_orders`（数量、单价、服务周期、有效天数快照）；没有此关联的订单自动视为 legacy，继续原来的人工处理路径，绝不补发新权益。

| 对象 | 状态 | 允许的后续操作 |
| --- | --- | --- |
| 支付订单 | pending_payment 待支付 | 经验证到账 → paid；没有任何支付会话时可取消或过期 |
| 支付订单 | paid 已付款 | 独立卡密/履约流；符合未交付条件时可进入 refund_pending |
| 支付订单 | refund_pending 退款处理中 | 权益冻结；经渠道核验全额成功 → refunded |
| 支付订单 | cancelled / expired / refunded | 终态，不重新发码 |
| 卡密 | available 待兑换 | 兑换 → reserved；管理员可冻结、作废；到期 → expired |
| 卡密 | reserved 已占用 | 同一兑换单继续处理；完成 → redeemed；取消/退款 → frozen |
| 卡密 | redeemed 已兑换 | 对应履约已完成；不可恢复为可兑换 |
| 卡密 | frozen 已冻结 | 从未提交兑换且订单仍已付，可解除冻结；有兑换历史的卡密不重新激活 |
| 卡密 | void / expired | 不能兑换或重新激活 |
| 履约单 | pending 待处理 | 指定负责人 → processing；取消 → cancelled 并冻结权益 |
| 履约单 | processing 处理中 | 可记阶段进度；完成 → completed；明确失败 → failed；结果不明 → review |
| 履约单 | failed 处理失败 | 原单回到 pending 重试，或取消冻结；不新建权益 |
| 履约单 | review 待核查 | 只能继续核查、确认完成、或凭证确认未交付后转 failed；不能直接重试 |
| 履约单 | completed / cancelled | 终态；完成必须有凭据编号和核验确认 |

季度是本站协助服务周期。处理人员需使用 processing 的阶段记录逐次记录服务，全部承诺交付完毕后才能确认 completed。支付订单的 paid 不因卡密使用而改成 completed。

## 一致性与授权

- 支付请求及通知复用官方签名、金额、币种、商户与渠道校验。金额 = 服务端单价 × 整数数量（1–10）。
- 所有权益操作先锁定 parent order：SQLite 使用串行事务队列及 BEGIN IMMEDIATE；PostgreSQL 使用 SELECT FOR UPDATE。再读取卡密和兑换单，锁顺序一致。
- 支付成功单独持久化。发码在独立事务中写入全部缺失序号与审计记录。`UNIQUE(order_id, ordinal)`、唯一卡密哈希和重复回调处理防止重复发码。
- 启动时及每 60 秒重试最多 50 笔已付缺码订单；后台也可触发补偿。单笔异常不影响其他订单。服务休眠期间不运行，唤醒后继续处理持久化积压。
- 卡密为 128 位随机值，演示 XYD 与真实 XYA 前缀不同。服务端同时检查来源订单的模式，前缀本身不作为授权。
- AES-256-GCM 加密保存原码，AAD 绑定卡密 ID；哈希用于检索。配置 `VOUCHER_SECRET` 为 32 随机字节的 64 位十六进制值；数据库保存指纹，错钥拒绝启动。缺钥关闭新购买及卡密展示，已有订单仍能查阅。
- 订单列表只有脱敏编号和状态。客户凭订单号 + 查询码通过 POST 显式展示仍可兑换的卡密，展示操作留审计。后台没有原始卡密读取功能。
- 兑换事务同时写入唯一兑换单并占用卡密。客户端每次新兑换生成 256 位随机 requestKey；数据库只存哈希；同一凭据和目标资料的重试返回原单。
- 浏览器会话只保存最近兑换查询凭据、待定请求的卡密指纹和随机查询码，不持久保存原始卡密。结果丢失后，凭卡密 + 原请求查询码可恢复同一兑换单。另一个查询码不能接管。
- 购买查询凭据与兑换查询凭据独立。购买者不能仅凭购买单查看兑换人的账号资料。客户兑换查询返回脱敏邮箱，后台详情读取会记录操作者会话指纹。
- 管理修改验证来源、会话和预期状态。限流覆盖卡密校验、展示、兑换及查询。错误日志不输出请求体、SQL 参数或机密信息。

## 退款与取消

当前自动化仅支持新卡密订单的全额退款对账。先申请退款，事务内冻结所有未交付权益并取消排队/已明确失败的兑换；存在 processing、review 或 completed 时拒绝。部分履约、部分退款、拒付争议仍需人工对账。

管理员在官方商户后台执行真实退款，本站不调用资金划转接口。然后输入微信商户退款单号 / 支付宝退款请求号 / Stripe refund ID，只读查询结果。服务端验证签名、原交易、订单、全额金额、币种（渠道提供时）及成功状态，才更新 refunded 并作废卡密。待确认、失败、部分金额或不匹配结果均保持冻结，不能手动伪造成功。演示退款只在演示环境中模拟，不调用支付网关。

微信使用 `GET /v3/refund/domestic/refunds/{out_refund_no}`；支付宝使用 `alipay.trade.fastpay.refund.query` 并开启响应验签；Stripe 使用当前支付会话关联的 PaymentIntent 与只读 refund 查询核对。实现通过本地签名/契约夹具验证，不代表真实商户权限及到账验证。

已退款订单收到重复付款通知不会恢复 paid 或产生新卡密。退款申请本身不提供“随意取消冻结”按钮，避免外部退款已经执行但本地尚未确认时重新售出权益。需要撤销退款申请的异常情况应先人工核对支付渠道与审计，再通过经过审查的恢复操作处理。

## 通知与未配置项

前台显示订单与履约时间线；未结束的履约每 15 秒查询状态，失败时可手动重试。无邮件、短信或即时通讯服务配置，不显示“消息已发送”。后台付款和履约设置展示缺少的环境变量名，不返回其内容。

正式收款仍需要微信/支付宝商户签约、密钥及 HTTPS 回调联调；实际开通需要运营人员、真实客服渠道和可履约价格。演示环境不能开通真实订阅。仓库不保存历史聊天中暴露的部署 API 密钥。
