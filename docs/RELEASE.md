# 上线、迁移与回滚

本次升级把“支付订单”“卡密”“兑换与履约单”拆成三个可独立审计的对象。数据库迁移只新增表和索引，不删除、不重写既有 `orders` 与 `order_events` 记录；没有 `purchase_orders` 关联的历史订单继续使用原来的订单处理流程，不会自动生成卡密。

## 发布前准备

1. 从需要上线的合并提交构建，并确认 CI 的 SQLite、PostgreSQL 和浏览器测试全部通过。
2. 备份 Neon 数据库，或创建带时间戳的数据库分支。记录当前 Render 部署的提交和数据库连接目标。
3. 生成一次 32 字节随机卡密密钥，并写入 Render 私有环境变量 `VOUCHER_SECRET`。它必须是 64 位十六进制字符串。
4. 把 `VOUCHER_SECRET` 与数据库备份分开安全保存。数据库保存密钥指纹；恢复旧数据库时必须使用当时的原密钥，错误密钥会让服务拒绝启动。
5. 保留现有的 `ADMIN_PASSWORD` 或 `ADMIN_PASSWORD_HASH`。二者只能配置一个。
6. 演示环境保持 `PAYMENT_MODE=demo`。真实收款需要另外完成商户签约、密钥、HTTPS 回调与到账联调，不能把演示通过当作真实交易通过。

可以在本机生成密钥：

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

不要把生成结果提交到 Git、发送到聊天或写进构建日志。历史对话中曾出现的部署密钥不适用于本次发布，也不得复用。

## 自动迁移

服务启动时执行 `server/migrations.ts`，过程是幂等的：

- 新增 `schema_migrations`、`purchase_orders`、`voucher_keys`、`vouchers`、`redemptions`、`commerce_events` 和 `refund_requests`。
- 为订单、卡密与履约查询建立索引。
- PostgreSQL 使用事务级 advisory lock，SQLite 使用串行写事务，避免多实例或并发请求重复初始化。
- 迁移不创建卡密，也不改变既有订单状态。历史订单在后台继续显示为旧处理流程。
- 新购买的 `order.amount` 仍是服务端计算的总额；`purchase_orders` 保存套餐单价、购买数量和权益期限快照。

若迁移失败，启动会中止，支付和订单接口不会以半迁移状态接收新业务。不要通过重建空数据库绕过迁移失败。

## 发布步骤

1. 先在一个使用一次性 PostgreSQL 数据库的预览服务启动新版本。
2. 检查 `/api/health`，确认 `status=ok`、`database=ok`、`databaseType=postgres` 和预期支付模式。
3. 用演示账号完成一次“下单 → 模拟付款 → 自动发两张卡密 → 只兑换一张 → 后台开始处理并填写演示凭据 → 顾客查询”。确认第二张卡密仍保持可兑换。
4. 在预览库查询 `schema_migrations.version = 1`，并抽查一张新订单对应 `purchase_orders`、`vouchers` 与兑换后的 `redemptions`。
5. 分别用旧订单凭据查询一笔历史订单，确认仍可查看并可走旧人工处理路径。
6. 检查 Render 日志没有输出卡密、请求体、数据库连接串或密钥。
7. 在低流量时段发布主站。启动后手动触发一次后台“补发遗漏卡密”，确认返回可处理状态。
8. 保留旧部署提交与数据库连接记录，观察支付回调、补发队列和兑换查询。

## 发码和补偿

支付确认与卡密写入是两个独立事务。支付结果一旦确认，订单保持 `paid`；发码暂时失败时由后台补偿队列重试。服务启动后立即尝试一次，之后每分钟处理最多 50 笔缺码订单。Render 免费实例休眠时不会运行定时器，唤醒后会继续处理持久化积压。

后台也会显示“补发遗漏卡密”按钮。补发只补写缺失序号，且数据库唯一约束保证同一订单的同一序号不会重复。不要通过修改订单状态或手工插入卡密解决发码失败。

## 状态迁移

| 支付订单 | 正常下一步 |
| --- | --- |
| `pending_payment` | 验签到账 → `paid`；未创建支付会话时可取消或由补偿任务标记 `expired` |
| `paid` | 新卡密流发放权益；满足退款前置条件时可申请 `refund_pending` |
| `refund_pending` | 原支付渠道确认全额成功 → `refunded` |
| `cancelled`、`expired`、`refunded` | 终态，不恢复为可付款、不发新卡密 |

| 卡密 | 正常下一步 |
| --- | --- |
| `available` | 兑换 → `reserved`；冻结、作废或到期 |
| `reserved` | 履约完成 → `redeemed`；取消/退款 → `frozen` |
| `redeemed` | 终态 |
| `frozen` | 只有从未提交过兑换时可按后台规则解除冻结；否则进入原兑换单或退款核查 |
| `void`、`expired` | 终态 |

| 兑换与履约单 | 正常下一步 |
| --- | --- |
| `pending` | 指定负责人 → `processing`；取消 |
| `processing` | 阶段进度；完成、明确失败或待核查 |
| `failed` | 回到原单 `pending` 重试，或取消 |
| `review` | 继续核查；确认完成，或凭证确认未交付后转失败 |
| `completed`、`cancelled` | 终态 |

完成履约必须填写可追溯的交付凭据并由处理人员确认。待核查状态不能直接变回待处理，避免不确定的外部操作被重复执行。

## 退款

新卡密订单的全额退款采用“先冻结、后核验”：

1. 后台申请退款，事务内冻结权益并取消排队中或已明确失败的兑换。
2. 存在处理中、待核查或已完成的履约时不接受该自动流程，需要先核查，部分退款和争议转人工对账。
3. 运营人员在微信商户平台、支付宝商户平台或 Stripe 后台执行真实退款。
4. 后台输入对应退款单号，仅调用只读查询。服务端验证签名、原交易、订单、金额与成功状态。
5. 只有全额成功才把订单改为 `refunded` 并作废全部卡密。结果未知时继续冻结，不能手工伪造成功。

演示退款只走演示状态，不调用支付网关。上线前需要用商户测试环境或授权的小额交易验证真实退款查询；本地合同测试只能证明代码路径与签名校验逻辑。

## 回滚边界

代码回滚本身不会删除新增表。旧版本会忽略这些表，已经产生的支付订单仍可读取。回滚时：

1. 立即暂停新订单、卡密兑换和履约操作。
2. 先导出 `purchase_orders`、`vouchers`、`redemptions`、`commerce_events`、`refund_requests` 和支付交易表，尤其保存待处理及待核查记录。
3. 把 `VOUCHER_SECRET` 与数据库快照一起保留。不要删除该变量，因为服务唤醒或前滚时仍需原密钥解密。
4. 将 Render 回滚到上一个经过验证的部署提交。旧代码不应接收新的卡密业务；等待处理前滚或人工完成待办。
5. 如果数据库备份整体恢复，必须恢复到与新代码提交兼容的时点，并核对支付渠道交易避免重复交付。

禁止执行 `DROP TABLE`、清空订单、重建正式数据库或更换 `VOUCHER_SECRET` 作为回滚手段。它们会破坏对账、卡密解密或历史订单。

前滚时重新部署已修复的提交，运行同一组迁移与健康检查。迁移幂等，可以重复执行。

## 验证命令

```bash
npm ci --include=dev --no-audit --no-fund
npm run build
npm test
npm run test:e2e
```

本地 PostgreSQL 集成测试需要一次性回环实例：

```bash
TEST_DATABASE_URL=postgresql://user:pass@127.0.0.1:5432/test npm test
```

测试工具会为每个夹具创建独立 schema，并在结束后删除该测试 schema。不要把正式 `DATABASE_URL` 当作 `TEST_DATABASE_URL`。真实微信、支付宝和 Stripe 到账及退款不在自动测试覆盖范围内，发布清单中应单独记录联调时间和交易凭据。
